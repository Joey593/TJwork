# 答辩演示路线与论文提纲

## 约 8 分钟演示

- 0:00–1:00：说明传统回归测试的问题及平台的角色。强调 LLM 是候选设计辅助，真实断言与审核是门禁。
- 1:00–2:00：工作概览、项目地址、需求点与追踪矩阵。说明所有数字来自实际运行数据库。
- 2:00–3:20：生成一组候选，展示 JSON 校验、模型名/Prompt/哈希/原始响应。未配置模型时如实说明使用规则对照。
- 3:20–4:30：人工检查预期和脚本，批准；编辑已有用例后显示新版本及待审核状态，证明无法绕过审核。
- 4:30–5:30：创建任务，HTTP 立即返回排队，查看真实浏览器执行结果、步骤与运行版本。
- 5:30–6:40：运行预置缺陷，展示错误堆栈、失败截图、Trace 和候选原因，避免将 AI 输出称为确定根因。
- 6:40–7:30：导出报告，展示 20 条批量、20 次重复实验和原始数据。
- 7:30–8:00：说明单实例、合成应用、小样本和真实模型实验待补充的边界。

## 论文建议结构

1. 绪论：课题背景、相关工作、问题定义与实现范围。
2. 技术基础：Playwright Locator/Trace、pytest Fixture/POM、FastAPI、Vue 3、关系数据库、LLM 结构输出。
3. 需求与总体设计：角色、业务闭环、非功能目标、架构、ER 关系与任务状态机。
4. 核心实现：声明式脚本、生成校验去重、人工审核与乐观锁、版本快照、后台执行、证据保存、报告与失败摘要。
5. 测试与实验：API 机制测试、界面验证、MySQL 持久化、20 条批量和稳定性；三组生成、定位、失败分类的实验设计及实际取得的数据。
6. 总结与展望：结论与证据对应，说明未测项目、统计限制，以及分布式队列、多租户、更多真实项目等后续工作。

## 常见问题

**创新在哪里？** 本科工程方法改进：受控 Schema、后置校验、人工审核、版本溯源与真实执行证据，将模型输出转化为可复查的工程流程。不要把单次 API 调用包装为模型创新。

**为何不用模型直接执行代码？** 当前业务需要可审查可控的测试资产。固定动作集合便于做字段校验、审核与复现，避免任意生成代码影响执行器。

**为何任务 API 能快速返回？** API 只做验证、快照与队列入库，pytest 在独立子进程运行；响应耗时与实际测试耗时分别测量。

**能否测任何网站？** 支持工程师配置目标与声明式步骤，已为典型场景提供映射；没有自主探索任意网站或自动推断业务 Oracle 的能力。

**0/20 偶发失败说明什么？** 只说明本次固定演示环境的观测值满足最低验收，不证明生产环境长期失败概率为零。

**模型实验未运行能写什么？** 写已经实现并测试的接口、Schema 与审核机制；将真实模型对照结果留空或标注待采集，不能把规则结果标成 LLM 效果。
